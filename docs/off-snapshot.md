# Локальный снимок Open Food Facts

Брендовые продукты («Овсяные отруби Мистраль», «Творожок Простоквашино»,
«Плавленый сыр Хохланд») есть только в Open Food Facts. Её публичный API
**троттлит анонимные запросы**: со страницы 503 — *«not available to anonymous
users… registered users are not subject to request limits»*. Замер 22.08.2026:
5 отказов из 8 запросов подряд, ответ за ~280 мс. Наш сервер ходит туда одним IP
за всех пользователей, поэтому попадание в бренд зависело от чужой нагрузки, а
пользователь видел «нет в базе» про существующий продукт.

OFF предлагает выход в тексте той же ошибки: *«if you're a bot, all our data can
be freely downloaded»*. Снимок — это он и есть.

## Что это даёт

| | было (живой API) | стало (снимок) |
|---|---|---|
| «отруби овсяные мистраль» | родовые отруби, если OFF ответит | «Отруби овсяные Мистраль» 369 ккал, **5 мс** |
| «сыр хохланд» | «сыр российский» 410 ккал | «Плавленый сыр Хохланд» 283 ккал |
| зависимость от 503 | полная | нет |

Загрузка при старте — 55 мс, память — 19 МБ, сеть при поиске не используется.

## Как обновить

Раз в месяц-два (OFF пополняется ежедневно, но наш срез — это хвост брендов, он
меняется медленно). **Делать локально, не на VPS**: там 4.9 ГБ памяти и 26 ГБ
диска, а распаковка выгрузки — это ~9 ГБ потока.

```bash
curl -L -o off-products.csv.gz https://static.openfoodfacts.org/data/en.openfoodfacts.org.products.csv.gz
cd server && npm run import:off -- ../off-products.csv.gz ./off-ru.jsonl ./off-ru-brands.txt
```

Скачивается 1.28 ГБ (~2 минуты), импорт стримит архив через gunzip — распакованные
9 ГБ на диск не пишутся. На выходе два файла: ~770 КБ данных и ~160 КБ марок.

Затем на сервер:

```bash
rsync -avz server/off-ru.jsonl server/off-ru-brands.txt fam:/opt/healthroutine-food/data/
ssh fam 'chown foodproxy:foodproxy /opt/healthroutine-food/data/off-ru*.txt /opt/healthroutine-food/data/off-ru.jsonl && systemctl restart healthroutine-food'
```

В `/opt/healthroutine-food/.env`:

```
OFF_LOCAL_PATH=/opt/healthroutine-food/data/off-ru.jsonl
OFF_BRANDS_PATH=/opt/healthroutine-food/data/off-ru-brands.txt
```

Переменная не задана ⇒ снимка нет и цепочка работает ровно как до него. В логе
при старте: `[off-local] 6377 продуктов, 9667 марок`.

## Что внутри и чего внутри нет

В выгрузке **50 016** русских продуктов. Полный состав (ккал + Б/Ж/У) есть у
**6 598**, после проверок правдоподобия и дедупликации осталось **6 377** — это и
есть база. У остальных **43 418 состава нет вовсе**: проверено и в CSV
(колонок на порцию не существует, килоджоулей тоже нет), и точечно через API —
он отдаёт `nutriments: {}`. Этих чисел не существует, их не прячут.

Что от тех 43 тысяч всё-таки взято: **словарь марок** (9 667 названий, включая
продукты без состава — имя марки там записано). Он делает определение бренда
точным вместо эвристического: см. `server/src/nutrition/specificity.ts`,
`setKnownBrands`.

Масса упаковки известна у 19 186 строк — пока не используется; это очевидный
кандидат на подстановку веса порции.

## Лицензия

Данные OFF — под **ODbL**: производную базу можно использовать и
распространять с указанием источника и под той же лицензией. Поэтому:

- каждая строка уходит клиенту с `source: 'openfoodfacts'` — ровно как ответ
  живого API, никакой подмены происхождения;
- файлы **не коммитятся в репозиторий** (он публичный, и это чужая база) — они
  артефакт деплоя, как `COMMUNITY_FOODS_PATH`.

## Почему не RAG и не векторный поиск

Задача лексическая: «мистраль» обязан отличаться от «ясно солнышко», а «молоко
3.2%» от «молоко 1%». Векторный поиск ищет похожее по смыслу и смазывает ровно
то различие, ради которого всё делается, — то есть возвращает подмену
конкретного продукта родовым (баг, из которого этот снимок и вырос). Плюс числа
в приложении никогда не приходят от модели (`docs/nutrition-science.md` §1), а
RAG втащил бы её обратно в путь, где считаются калории.

Вместо этого — инвертированный индекс «основа слова → строки» поверх
существующего матчера `ruSearch` (падежи, полуслова, одна опечатка). 6 тысяч
строк, отклик 1–5 мс, ноль внешних вызовов.

## Индекс по штрихкодам

Отдельный срез той же выгрузки: **весь мир по коду**, а не русские продукты по
названию. Полный состав есть у 2 197 807 продуктов, из них валидный EAN — у
2 150 146; после проверок правдоподобия в индексе **2 054 787** товаров.
Русских среди них всего 6 664 — то есть по штрихкоду выигрыш кратно больше, чем
по названию: это все привозные и импортные пачки, которые по-русски не ищутся.

```bash
cd server && npm run import:barcodes -- ../off-products.csv.gz ./off-barcodes
```

Два файла: `off-barcodes.bin` (47 МБ, записи по 24 байта, отсортированы по коду)
и `off-barcodes.names` (55 МБ). Формат описан в `src/nutrition/barcodeIndex.ts`.

Читается **двоичным поиском прямо с диска**: ~21 чтение по 24 байта на запрос.
Замер: открытие 14 мс, **8 МБ кучи на 2 миллиона товаров**, один поиск —
**20 микросекунд**. В память ничего не грузится, SQLite не нужен.

```
OFF_BARCODES_PATH=/opt/healthroutine-food/data/off-barcodes
```

Переменная не задана ⇒ поиска по коду нет, остальное работает как обычно.

Контрольная цифра EAN-13 проверяется ДО обращения к базе: искажённое считывание
отбрасывается, а не превращается в чужой продукт. Это же свойство делает
штрихкод честным ключом там, где имя ненадёжно.
